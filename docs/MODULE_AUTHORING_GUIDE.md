# Qdigo Module Authoring Guide

**Audience:** an LLM session (or a person) turning lecture material, usually a PDF deck, into a complete, importable **guided learning module** for the Qdigo site.
**Contract:** follow this document exactly. The site validates every module against it on import and rejects anything that doesn't conform.
**Schema version covered:** `schemaVersion: 1`, **guide edition 2** (declare `guide: 2` in the manifest; §1.1).

---

## 0. For the human: how to use this guide

Start a new chat (ideally inside the "bdcc midterms reviewer" Claude Project, where this guide already lives) and attach:
1. the lecture PDF,
2. this file (`MODULE_AUTHORING_GUIDE.md`),
3. `WIDGETS.md` (generated by the site: Admin → "Download widget reference"; it's always up to date),
4. *(recommended)* a reference module as a bundle: Admin → `fim` → "Export as bundle text" for a **code** course; for a **journal** course (accounting), §6b has a complete worked excerpt, and with the repo you can bundle the demo: `pnpm kodigo pack packages/schema/test/fixtures/joc-demo`.

Then paste:

```text
Build a Qdigo study module from the attached lecture, following MODULE_AUTHORING_GUIDE.md (guide edition 2) exactly.

Module id: <kebab-case-id>
Title: <full title>
Short title (≤ 12 chars): <course-menu label>
Course: <course code, e.g. BDCC or MANACC> (exactly as the course's other modules spell it)
Workbench: <code | journal>   (code = Math & Code with Python; journal = Math & Journal for accounting)
Tab label: <optional, e.g. Analysis>   (renames the second tab; copy it from the course's other modules)
Lecture: Sessions <x–y>, dated <yyyy-mm-dd>
Prerequisite modules: <ids, or none>
Anything my professor emphasized / exam format notes: <optional>

Work in the order the guide prescribes (SOURCE_NOTES → datasets → logic.js → examples → verify → glossary → the rest).
Output a single bundle in the bundle text format. Do not abbreviate any file.
```

Import it via **Admin → Import → Paste LLM output**. If validation fails, click **"Copy fix request for LLM"**, paste that into the same chat, and re-import the corrected files.

*With repo access (Claude Code):* write the files to `modules/<id>/`, run `pnpm kodigo validate modules/<id>` until it's clean, then `pnpm kodigo pack modules/<id>`.

## 1. Your task (for the LLM)

Produce **one module**: a folder of files that **teaches** one topic, not just reviews it. A learner who has never seen the lecture, and who knows **nothing** of the subject beyond everyday words, should be able to follow the module's Path from the first scene to the mastery check and come out able to do everything the lecture's examples do, by hand. Write for that learner (§7.6). The site does the guiding: it sequences the lessons, checks every prediction, hands out fresh practice questions, gives hints, and tracks mastery. Your job is to supply the content those features run on.

| Tab | Purpose | File |
|---|---|---|
| **Path** | the module's learning objectives and every lesson step in teaching order, with progress and a "Continue" button (built automatically, §7.0) | `manifest.yaml` (`objectives`) |
| **Intuition** | guided, animated, interactive scenes in the style of a 3Blue1Brown video. Every **term** is defined here, at the moment the picture shows it, and the math is built up *inside* the visuals | `intuition.yaml` |
| **Math & Code** or **Math & Journal** | derivations side by side with the **workbench**: Python code (`workbench: code`) or journal entries, schedules and T-accounts (`workbench: journal`). Each formula term is linked to the lines that compute or record it, and every section ends with "Your turn" practice | `math-code.yaml` |
| **Application** | a notebook-style case study that ties it all together, plus how it's done at scale (or in practice) | `application.yaml` |
| **Quiz** (per course) | parameterized question templates; numbers change every time; hints on request | `quiz.yaml` |

Behind them sit `logic.js` (all computation), `datasets/` (all data), `examples.yaml` (the lecture's own numbers, used as tests), `glossary.yaml`, `manifest.yaml`, and `SOURCE_NOTES.md` (your extraction of the source).

**You never write UI code.** You compose widgets from a fixed catalog (§9) and supply pure functions. The site renders, animates and grades.

### 1.1 Guide edition 2: guided learning

Set `guide: 2` in the manifest. It turns these rules from warnings into **import errors**:

- every glossary term is introduced in an Intuition beat (`define:`, §7.1a);
- in a `workbench: journal` module, every math section has a `journal` pane.

And it turns on these lints: 3–6 `objectives`; ≥ 3 `practice` gates and ≥ 2 `reflect` gates across the scenes; `tryIt` on every math section; `hints` on at least half the quiz templates (§7.4). Modules without `guide: 2` (edition 1) still import, and they get the same checks as warnings.

### 1.2 Workbenches: code or journal

The second study tab pairs each derivation with a **workbench**: the place where the learner sees the idea *done*. Pick it per course with `workbench:` in the manifest.

**Tab label.** The tab is called Math & Code or Math & Journal unless the manifest sets `workbenchLabel` (≤ 20 characters). Courses whose second tab is not really math or code, such as framework-heavy business courses, set one name for the whole course and every module in it uses the same one (INTB uses `workbenchLabel: Analysis`). The dashboard ring shows its first word.

| | `workbench: code` (default) | `workbench: journal` |
|---|---|---|
| Typical courses | BDCC, ML, data science | Managerial / cost / financial accounting |
| Tab label | Math & Code | Math & Journal |
| Section pane | `code` (Python, ≤ 30 lines + docstrings), `extraCode` | `journal`: blocks of **entries** (general journal), **schedules** (statements, cost sheets, budgets, production reports) and **T-accounts** (§5.8b) |
| Anchors | `# @a name` markers in code | `anchor: name` on journal lines, schedule rows, T-accounts and postings |
| Step through | one trace step per executed line, per loop iteration | one trace step per amount computed or posted, in the order an accountant would work it |
| Workbench quiz types | `code-fill` | `journal-entry`, `schedule-fill` |
| Tag | `code` | `journal` |
| Stage widgets | TransactionTable, Matrix, Code… | Journal, TAccounts, Schedule (plus Chart, Slider, Readout…) |
| Application `atScale` | the big-data version (PySpark, SQL…) | "in practice": how a company does it (ERP or spreadsheet set-up, month-end close, controls, PFRS/PAS disclosure if the lecture covers it) |
| Money | — | `currency` (default `₱`), `|money` interpolation, amounts formatted with thousands separators |

Everything else (Intuition, glossary, examples, quiz engine, Application) works the same for both.

## 2. Mandatory workflow

Do these in order. Don't skip steps 1–4; they are what makes the module *correct*.

1. **Extract** → write `SOURCE_NOTES.md` (§5.2): every concept in lecture order, every formula verbatim, **every worked example with exact numbers and slide refs**, conventions, ambiguities, errata. For accounting, also every **journal entry, schedule and statement** the lecture shows, with its account titles exactly as printed.
2. **Model the data** → `datasets/*.yaml` (§5.3), using the lecture's own examples first.
3. **Implement** → `logic.js` (§5.4): one pure function per formula, algorithm or schedule, with traces for anything step-by-step. Journal modules also return the **entries / schedule rows / T-accounts** a section shows (§5.8b).
4. **Verify** → `examples.yaml` (§5.5): encode every worked example from step 1 as fn + input → expected output. **Mentally execute (or actually run, if you have a tool) every example against your `logic.js`.** If a number doesn't reproduce, your *convention* is wrong. Revisit `SOURCE_NOTES.md` → *Conventions*. Only call it a slide error (errata) if you can show that the slide contradicts itself or basic arithmetic.
5. **Glossary** → `glossary.yaml` (§5.6): every term the lecture uses. You'll introduce each one in a scene (step 9).
6. **Objectives and skills** → plan 3–6 `objectives` ("By the end you can…", each tied to skills) and 6–12 `skills` (§5.1). The objectives are the promise the Path makes; every later file serves them.
7. **Quiz** → `quiz.yaml` (§5.10) plus generators in `logic.js`. Write it *before* the lessons, because lessons embed quiz templates as practice (`practice` gates, `tryIt`). Give templates `hints`.
8. **Math & Code / Math & Journal** → `math-code.yaml` (§5.8): one section per formula, algorithm, entry set or schedule; each ends with `tryIt`.
9. **Intuition** → `intuition.yaml` (§5.7): scenes that build each idea from a concrete question, **define every glossary term where it first appears** (§7.1a), and include practice and reflect gates.
10. **Application** → `application.yaml` (§5.9).
11. **Manifest** → `manifest.yaml` (§5.1): `guide: 2`, `workbench`, objectives, skills covering everything referenced, `requires.widgets`.
12. **Self-check** → go through the checklist in §12 and fix issues before outputting.

## 4. Shared syntax (used in every file)

### 4.1 IDs
- Pattern `^[a-z0-9]+(-[a-z0-9]+)*$` (kebab-case), unique **within their kind** in the module.
- IDs are **permanent**: progress is keyed on them. When revising a module, never rename an existing ID.
- Item names inside datasets (e.g. `bread`, `kape-3in1`) follow the same pattern. Put pretty names in the dataset's `labels`.
- Matrix row and column labels: letters, digits, `_` or `-` only (no spaces or commas), e.g. `HP1`, `A`, `u1`.

### 4.2 Markdown (`Markdown` fields)
CommonMark + GFM tables. Inline math `$…$`, display math `$$…$$` (KaTeX). Interpolation `{=…}` is allowed (§4.4). Keep prose short (word limits in §11).

**Term links.** `[[term-id]]` shows the glossary term's name; `[[term-id|shown text]]` shows your own words (use it mid-sentence: `its [[manufacturing-overhead|manufacturing overhead]]`). Either renders as a dotted-underlined word whose hover card gives the term's definition. Use them in narration, summaries, prompts and explanations whenever a term appears *after* the beat that defines it. Every id must be a glossary term (validated).

### 4.3 TeX (`Tex` fields) and math anchors
- KaTeX-compatible LaTeX only (no `\usepackage`, no `align` environments; use `\begin{aligned}…\end{aligned}` inside display math).
- **Anchor a term** so the site can link it to code and to trace steps: `\anchor{name}{content}`, for example
  `\frac{\anchor{sup-ab}{\text{Sup}(A \cup B)}}{\anchor{sup-a}{\text{Sup}(A)}}`.
  Anchor names use `[a-z0-9_-]+` (**lowercase only**: `solve-v`, not `solveV`; a camelCase name is silently not an anchor and
  the validator reports it as missing), and the same name may appear in several steps. The same rule applies to code anchors (§4.6)
  and to the `code`/`math` names in trace steps.

### 4.4 Interpolation `{=path|format}`
Inserts a live value from the current **scope** (§4.5) into Markdown or TeX.

| Format | Result |
|---|---|
| *(none)* | numbers: rounded to 2 dp, trailing zeros stripped (`0.5`, `2.5`, `0.67`); strings as-is; arrays as `a, b, c` |
| `\|0`…`\|6` | round to N dp, strip trailing zeros |
| `\|2f` (any N) | fixed N dp (keeps zeros: `0.50`) |
| `\|frac` | exact-looking fraction if the denominator ≤ 12 (`10/3`, `-7/3`), else 2 dp |
| `\|pct` | percentage, 0 dp (`40%`); `\|pct1` for 1 dp |
| `\|int` | integer |
| `\|comma` | thousands separators, up to 2 dp (`1,234,567.89`); `\|comma0`, `\|comma2` fixed dp |
| `\|money` | currency: `₱61,000` (0 dp when whole, else 2: `₱1,250.50`); `\|money2` always 2 dp (`₱15.00`). Negative → `−₱300`. In TeX the peso sign and commas are escaped for you |
| `\|set` | itemset: in TeX → `\{\text{bread}, \text{milk}\}`, in Markdown → `{bread, milk}` (uses dataset labels) |
| `\|list` | `a, b, c` |
| `\|text` | TeX only: wraps a string in `\text{}` |

Paths use dots: `{=c.conf|2}`, `{=freq.count}`, `{=pair.0}`.

### 4.5 Scope and references `@path`
Every scene, section, case study and quiz instance has a **flat scope** made of:
1. **datasets** listed in `data:` (by id; the value is the dataset payload, see §5.3),
2. **state** keys (`state:`; widgets can change them),
3. **derived** values (`derive:` outputs, recomputed whenever state changes),
4. in quizzes: **generator vars**.

Names must not collide across these four sources. **State keys, `derive.out` names and generator vars are identifiers** (`^[A-Za-z_][A-Za-z0-9_]*$`, camelCase recommended, e.g. `minsup`, `freq`, `supAB`), because `when` expressions and dot paths use them. Dataset IDs used in `when` expressions must not contain hyphens (`grocery5`, not `grocery-5`); for datasets that's recommended anyway.

A YAML value that is a string starting with `@` is a **reference**: `'@grocery5'`, `'@freq.supportMap'`, `'@c.conf'`. References must be the *entire* value (use `{=…}` for text). **Always quote references in YAML** (`'@x'`), because `@` is reserved.

### 4.6 Code anchors
In `code.source`, mark lines that implement an anchored math term. The markers are removed before display.

```python
def confidence(A, B, transactions):
    # @a sup-ab
    sup_ab = abs_support(A | B, transactions)
    # @end
    sup_a = abs_support(A, transactions)      # @a:sup-a
    return sup_ab / sup_a                      # @a:ratio
```
- Block form: a line containing only `# @a name` starts the block, and `# @end` closes the most recent open block. Blocks may nest.
- Single-line form: a trailing `# @a:name`.
- Comment prefixes: `#` (python, bash, yaml, r), `//` (js, ts, java, c, scala), `--` (sql).
- **Every anchor used in a section's TeX must exist in its code, and vice versa** (validated).

**Journal anchors** (`workbench: journal`). There are no comment markers: put `anchor: <name>` on the journal line, schedule row, T-account or posting that records or computes the term. The same name may sit on several items (the schedule row that computes applied overhead *and* both lines of the entry that records it). The pairing rule is the same: every `\anchor{x}` in the derivation has at least one journal item with `anchor: x`, and vice versa. When a block's list comes from logic.js (`entries: '@close.entries'`), the anchors inside it are paired at the logic step, after the list is resolved.

### 4.7 Selectors, tones, commands
Widgets are addressed with **selectors** (strings, per widget, listed in §9), such as `row:3`, `set:bread,milk`, `cell:A,HP1`, `term:sup-ab`, `anchor:sup-ab`.
**Tones:** `accent` (focus), `good` (kept, frequent, correct), `bad` (pruned, wrong), `warn`, `muted`.
**Common commands** (all widgets): `highlight {sel, tone?}`, `pulse {sel}`, `annotate {sel, text}`, `clear {sel?}`.

**Persistence rule:** `highlight` and `pulse` are *transient*: they last for the current beat or trace step only. Every other command (`strike`, `prune`, `fill`, `project`, `annotate`, `center`, …) *persists* until the scene or player resets. The engine rebuilds state by replaying persistent commands, which is what makes back and scrub work, so commands must be deterministic.

### 4.8 YAML rules (avoid parser errors)
- 2-space indentation, no tabs, and no anchors or aliases (`&`, `*`).
- Use a **block scalar `|`** for any Markdown or TeX longer than a few words, and for anything containing `\`.
- Use **single quotes** for short strings containing `: # { } [ ] @ & * ! | > % ,` or starting with a special character. Inside single quotes, write `''` for a literal `'`.
- **Never use double quotes for TeX** (backslash escapes break it).
- Numbers that must stay strings (dates, `3-4`) go in quotes.

## 5. File specifications

The TypeScript types below are **normative**: the site's validator implements them. `?` means optional.

```ts
type Id = string;                 // kebab-case, §4.1
type Markdown = string;           // §4.2 (+ {=} §4.4)
type Tex = string;                // §4.3 (+ {=} §4.4)

type Value = string | number | boolean | null | Value[] | { [k: string]: Value };
type Prop = Value | Ref;
type Tone = 'accent' | 'good' | 'bad' | 'warn' | 'muted';
```

### 5.1 `manifest.yaml`

```ts
interface Manifest {
  schemaVersion: 1;
  id: Id;                          // permanent
  version: string;                 // semver; bump when you revise
  title: string;
  shortTitle: string;              // ≤ 12 chars (label in the course menu)
  summary: Markdown;               // ≤ 50 words
  course?: string;                 // course code, e.g. BDCC. Always set it (see "Courses" below)
  order?: number;                  // position in the course's menu (10, 20, 30…)
  color?: string;                  // hex accent, e.g. '#0ea5e9'
  icon?: string;                   // a lucide icon name, e.g. shopping-basket, users, grid-3x3
  sources: { title: string; file?: string; sessions?: string; date?: string }[];
  prerequisites?: Id[];            // other module ids
  skills: { id: Id; label: string; description?: string }[];   // 6–12 skills
  requires: { widgets: string[] }; // every widget name used anywhere in the module
  guide?: 1 | 2;                   // authoring-guide edition; write 2 (§1.1)
  workbench?: 'code' | 'journal';  // default 'code' (§1.2)
  workbenchLabel?: string;          // ≤ 20 chars; renames the second tab, same value across a course (§1.2)
  currency?: string;               // journal modules: symbol for amounts and |money (default '₱')
  objectives?: { id: Id; text: string; skills?: Id[] }[];      // 3–6 learning objectives (guide 2)
  authoring?: { generatedBy?: string; generatedAt?: string; notes?: string };
}
```

**Objectives** are what the learner can *do* after the module, written as one sentence each, starting with a verb and checkable: "Compute a predetermined overhead rate and explain why it is set before the year starts", not "Understand overhead". Tie each to the skills that prove it; the Path shows a mastery bar per objective from those skills' quiz scores. Together the objectives cover every skill.

**Courses.** `course` is the code of the course the module belongs to, e.g. `BDCC`. The site groups modules by it: the
top bar has one dropdown per course listing its modules, and **a quiz only ever draws from one course**. Use exactly the
code the user gives you, with the same spelling and case as the course's other modules, because a different code creates
a separate course. If `course` is missing, the site files the module under its default course and the validator warns.
`order` sorts modules inside their course's menu.

### 5.3 `datasets/<id>.yaml`

```ts
type Dataset =
  | { id: Id; kind: 'transactions'; title?: string; source?: string; description?: Markdown;
      labels?: Record<string, string>;                       // item id → display label
      transactions: { id: string | number; items: string[] }[] }
  | { id: Id; kind: 'matrix'; title?: string; source?: string; description?: Markdown;
      rows: string[]; cols: string[]; values: (number | null)[][] }   // null = missing
  | { id: Id; kind: 'table'; title?: string; source?: string; description?: Markdown;
      columns: string[]; rows: Value[][] }
  | { id: Id; kind: 'list'; title?: string; source?: string; items: Value[] }
  | { id: Id; kind: 'json'; title?: string; source?: string; value: Value };
```

**Payload seen through `@id`:** transactions → the `transactions` array; matrix → `{rows, cols, values}`; table → `{columns, rows}`; list → `items`; json → `value`. Labels from all datasets are merged into a module-wide label map that widgets and `|set` use automatically.

Rules: the lecture's examples come first and are **verbatim**. Application datasets should be realistic and small (≤ 40 rows; matrices ≤ 10×12). Local flavor (Philippine context) is welcome.

### 5.4 `logic.js` (all computation lives here)

A **plain ES module with no imports and no build step**. It runs inside a Web Worker.

```js
export default function register(sdk) {
  // helpers you need, destructured from sdk
  const { isSubset, sortSet, key, powerset, round } = sdk;

  function support({ transactions, itemset }) { /* … */ return { abs, rel, hits }; }
  function confidence({ transactions, A, B }) { /* … */ return { supAB, supA, conf, trace }; }

  function confidenceQ({ rng, difficulty, fns, sdk }) { /* … */ return { vars, misconceptions }; }

  return {
    fns: { support, confidence /* , … */ },
    generators: { confidenceQ /* , … */ },
  };
}
```

**Rules for `fns`:**
1. **Pure and deterministic.** No `Math.random`, `Date`, `fetch`, DOM, timers, or state shared between calls.
2. **One object argument in, one plain object out.** Never return a bare number: FunctionPlot fns return `{ y }`. Output must be JSON-serializable (no `Set`/`Map`/`undefined`; use `null`).
3. **Canonical outputs:** itemsets are arrays sorted by a stated order (use `sdk.sortSet`); lists of results are sorted deterministically.
4. **Full precision.** Never round inside fns (display formatting and example tolerances handle it). *Exception:* if the lecture explicitly rounds intermediates and that changes a result, add an option such as `roundIntermediate: 2` and document it in SOURCE_NOTES.
5. **Fast:** < 50 ms per call at module data sizes; traces ≤ 400 steps.
6. Anything that is a step-by-step process in the lecture returns a **`trace`** (below).
7. fns can call each other directly (they're in the same closure).
8. **Journal workbench:** a fn whose result fills a journal pane or widget returns plain lists in the §5.8b shapes, e.g. `entries: [{ id, date?, lines: [{ account, debit | credit, anchor? }], memo? }]`, `rows: [{ id?, label, amount | amounts, style?, format?, anchor? }]`, `accounts: [{ id, name, debits: [{ amount, ref? }], credits: [...] }]`. Amounts are **positive**: the side (debit or credit) carries the sign. When the side depends on the numbers (over- vs underapplied, favorable vs unfavorable variance, gain vs loss), the fn builds the lines, so the entry is always right for the live inputs.

**Trace format** (drives `StepPlayer`, math↔code step-through, and animations):

```ts
interface TraceStep {
  label: Markdown;                         // ≤ 20 words; {=…} can use this step's vars
  code?: string;                           // code anchor to light up (role 'code')
  math?: string;                           // TeX anchor to light up (role 'formula')
  vars?: Record<string, Value>;            // shown as debugger-style badges; available to label
  ops?: { role: string; cmd: string; args?: Value }[];  // widget commands addressed by ROLE
  patch?: Record<string, Value>;           // state patch applied at this step (undone on reset/seek back)
}
```
Roles are abstract names (`table`, `lattice`, `matrix`, `sims`, `code`, `formula`…) that the scene maps to concrete widget IDs in `StepPlayer.props.roles`. Document the roles each trace fn uses in a comment above it.

**Rules for `generators`** (quiz):

```ts
type Generator = (ctx: { rng: Rng; difficulty: 1 | 2 | 3; fns: Fns; sdk: Sdk }) => {
  vars: Record<string, Value>;                   // merged into the question's scope
  options?: Markdown[];                          // for mcq/multi (overrides static options)
  answer?: number | number[];                    // option index(es) for mcq/multi
  misconceptions?: { var?: string; value?: number; feedback: Markdown;
                     for?: string | string[] }[];   // the answer var(s) this mistake produces, e.g. for: 'endWip'
};
```
- **Key every generator misconception with `for`.** One generator usually serves several templates (equivalent units, unit cost, completed cost…). A misconception keyed `for: 'euConv'` is attached only to templates and hand-calc steps whose answer `var` is `euConv`; an unkeyed one goes to every `numeric` template of that generator (never to hand-calc steps). Unkeyed misconceptions on a shared generator end up as feedback about the wrong quantity.
- Compute answers **by calling `fns`**, so quiz answers and lessons can never disagree.
- Produce **hand-computable** problems: small tables (≤ 8 transactions, ≤ 6 items, matrices ≤ 5×6), integer ratings, results with small denominators. Difficulty 1 = one step on a tiny table; 3 = a multi-step computation on a lecture-sized table.
- **Reject ambiguous draws** and redraw (loop with `rng`): ties at a top-k cutoff, zero denominators, answers equal to a misconception value, degenerate cases (everything frequent, all similarities 0).
- Put every value the prompt, visuals, explanation and steps need into `vars`.

**`practice`** embeds one of your quiz templates (by id) under the narration with fresh numbers, its hints, instant feedback and "New numbers"; Next unlocks once the learner checks an answer (or skips). **`reflect`** asks for a short explanation in the learner's own words (≥ 3 words), then reveals your `model` answer (≤ 80 words) to compare against; the text is saved to the learner's notes. `when` expressions use Qdigo's own small, sandboxed expression parser (no `eval`): `==, !=, <, <=, >, >=, and, or, not, + - * / %`, parentheses, numbers, `'strings'`, `true`/`false`/`null`, dot paths (`freq.count`, `pair.0`), plus the functions `len(x)`, `has(arr, v)`, `abs(x)`, `round(x, d)`, `min(…)`, `max(…)`. Example: `'freq.count == 1 and minsup >= 4'`.

Use `do` commands for emphasis and for structural moves (`prune`, `project`, `center`, `focus`…), and a `StepPlayer` to play an algorithm's trace across several widgets. **Keep the same widgets on stage across beats** and change what they show; don't swap widgets. ### 5.8b The journal pane (`workbench: journal`)

In an accounting module, each section pairs its derivation with a **journal pane** instead of (or, rarely, as well as) code. A pane is an ordered list of blocks; the site renders them one under another, links their anchors with the derivation, recomputes every amount from the section's live inputs, and lights them up as the learner steps through.

```ts
  id?: Id; label: Markdown;
```

### 5.10 `quiz.yaml`

```ts
interface QuizFile { templates: Template[] }
interface Base {
  id: Id; skills: Id[]; difficulty: 1 | 2 | 3;
  tags: ('term' | 'intuition' | 'math' | 'code' | 'journal' | 'application')[];

  data?: Id[];                      // datasets in scope
  prompt: Markdown;
  show?: StageWidget[];             // visuals (tables, matrices…); props may reference generator vars

  hints?: Markdown[];               // progressive hints, revealed one at a time in practice (nudge → method → first step)
  calculator?: boolean;             // quiz calculator: true = open it for this question, false = keep it closed (default by type, below)

                             optionFeedback?: Record<string, Markdown> }                             // key = option index
interface Multi extends Base { type: 'multi'; options?: Markdown[]; answer?: number[]; shuffle?: boolean }

                          relTol?: number; accept?: ('decimal' | 'fraction' | 'percent')[];   // default [decimal, fraction]; without 'decimal' a plain number is rejected
                          percent?: boolean }   // answer in % units (98.59): 98.59, 98.59% and 0.9859 all accepted (§7.1b)

interface Numeric extends Base { type: 'numeric'; answer: NumericAnswer; misconceptions?: Misconception[] }
interface CodeFill extends Base { type: 'code-fill'; lang?: string; code: string;   // contains __BLANK_1__, __BLANK_2__, …
                                  blanks: Record<string, { accept?: string[]; regex?: string; hint?: string }> }
interface Match extends Base { type: 'match'; pairs: [Markdown, Markdown][]; pick?: number }   // pick = random subset size
interface Order extends Base { type: 'order'; items: Markdown[] }                                // listed in the CORRECT order
interface HandCalc extends Base { type: 'hand-calc';
  steps: { prompt: Markdown; answer: NumericAnswer; misconceptions?: Misconception[]; hint?: Markdown }[] }
interface JournalEntryQ extends Base { type: 'journal-entry';
  accounts: string[] | Ref;         // the chart of accounts offered in the dropdowns: every answer account + ≥ 2 plausible distractors
  entries: { id?: Id; date?: string; prompt?: Markdown;
             lines: { account: string; debit?: number | Ref; credit?: number | Ref }[] }[] | Ref;   // the expected entries
  tol?: number; relTol?: number }   // amount tolerance; default 0.01 abs or 0.05% relative
interface ScheduleFillQ extends Base { type: 'schedule-fill';
  columns?: string[];
  rows: (ScheduleRow & { blank?: boolean; given?: number[]; tol?: number })[] | Ref;   // rows with blank: true become inputs; given = columns of that row printed, not asked (e.g. [0] keeps the physical-units column of an EU row)
  tol?: number; relTol?: number }
type Template = Mcq | Multi | Numeric | CodeFill | Match | Order | HandCalc | JournalEntryQ | ScheduleFillQ;
```
- A question instance is `(template id, seed)`. Everything must render from the generator's `vars` plus static fields.
- **Code-fill matching** ignores all whitespace and treats `'` and `"` as equal, so keep `accept` lists minimal but include genuine alternatives (`len(transactions)` and `len(D)` if both are valid in context).
- **Misconceptions** are *specific wrong methods*, computed by the generator (`var`) or fixed (`value`), with feedback that names the mistake. The engine ignores any that coincide with the correct answer.
- Glossary questions are auto-generated. **Don't** write plain "define term X" templates; write `term`-tagged templates only for richer conceptual distinctions.
- **Hints** go from a nudge to the method to the first step, and never state the final answer. Every numeric, hand-calc, journal-entry and schedule-fill template gets 1–3 hints (hand-calc steps also keep their per-step `hint`).
- **Calculator.** In a `workbench: journal` module the quiz offers a desk calculator on every question and opens it by itself for `numeric`, `hand-calc`, `schedule-fill` and `journal-entry` templates. Set `calculator: false` when the arithmetic is already done in the prompt (e.g. "record the transfer of ₱X"), and `calculator: true` on an `mcq`/`multi` that needs computing before choosing. In other workbenches it only appears on templates with `calculator: true`.
- **journal-entry** grading: accounts match case-insensitively, line order doesn't matter, repeated accounts are netted. Each expected account earns its share when it is on the right side with the right amount; each account that doesn't belong costs one share. The learner gets specific feedback: wrong side, amount off, missing account, stray account, "debits and credits are reversed", and "your debits don't equal your credits". When the side depends on the numbers (over/underapplied, favorable/unfavorable), let the generator return `entries` and `accounts` (`entries: '@entries'`) built by the same fn the lesson uses, and shuffle the accounts list.
- **schedule-fill** shows a statement or schedule with some rows blank; each blank cell is graded like a numeric answer (rows with `format: pct` also accept `40%`). Learners may type `₱12,500`, `12,500` or `(1,200)` for negatives in money rows.
- **How typed numbers are read.** Commas count only as thousands separators (`2,5` is rejected, not read as 25). In a `numeric` or `hand-calc` answer, `(500)` means −500 only when the expected answer is negative; otherwise parentheses are grouping, so `(2/3)` is 2/3. In journal-entry Debit/Credit cells amounts must be positive: the column is the side.
- **State the rounding whenever the answer isn't a whole number.** If 76% of a generator's answers are decimals like 27.78, a tolerance of 0.1 marks `28` wrong: either say "to one decimal place" in the prompt or loosen `tol` to match the rounding you ask for. Do the same for hand-calc steps.
- **Misconceptions must stay distinguishable.** If a generator's warned-against method (plain average vs F1, plain accuracy vs balanced accuracy, unclipped vs clipped rating) lands within the tolerance of the right answer, the engine drops that misconception and the wrong method is graded correct. Redraw until the gap is at least 3× the tolerance, and key every misconception to the quantity *its* template asks for (a hint about equivalent units doesn't belong on a unit-cost answer).
- **Generated wording must match the numbers.** If an option or explanation states a verdict ("adds little", "a loss"),
  constrain the draws so the verdict holds for every seed (sweep a few hundred), and if the answer always has the same
  sign, draw some cases on the other side. For a signed answer, never use its absolute value as an unconditional
  misconception (it equals the answer half the time); use −answer, keyed to that step.
- **Rounding and ranges.** "One decimal place" needs a tolerance slightly above half a unit (0.06, not 0.05). Range or
  bucket MCQs must be contiguous, correctly labelled, at one precision, with `shuffle: false`. Printed arithmetic with
  rounded intermediates must still give the printed result.
- **Distractors** are plausible, in the same vocabulary and length as the right answer, and unambiguously wrong: no
  textbook edge case that is arguably right, and check another module's data before writing a "wrong" claim about it.
- **match:** the right-hand labels may repeat (two "Value-added" cards are interchangeable when graded), but avoid labels that give the pairing away by sharing words with the left side.

**`logic.js`** (excerpt)
```js
export default function register(sdk) {
  const { isSubset, sortSet, key, powerset } = sdk;
  const ORDER = ['bread', 'butter', 'cheese', 'eggs', 'milk', 'yogurt']; // lecture uses alphabetical order

  function support({ transactions, itemset }) {
    const set = sortSet(itemset);
    const hits = transactions.filter(t => isSubset(set, t.items)).map(t => t.id);
    return { abs: hits.length, rel: hits.length / transactions.length, hits };
  }

  // roles: table (TransactionTable), code, formula
  function confidence({ transactions, A, B }) {
    const both = support({ transactions, itemset: [...A, ...B] });
    const ante = support({ transactions, itemset: A });
    const conf = ante.abs === 0 ? null : both.abs / ante.abs;
    return {
      supAB: both.abs, supA: ante.abs, conf,
      trace: [
        { label: 'Baskets containing A ∪ B: {=supAB}', math: 'sup-ab', code: 'sup-ab',
          vars: { supAB: both.abs },
          ops: [{ role: 'table', cmd: 'highlight', args: { sel: both.hits.map(id => `row:${id}`), tone: 'good' } }] },
        { label: 'Baskets containing A: {=supA}', math: 'sup-a', code: 'sup-a',
          vars: { supA: ante.abs },
          ops: [{ role: 'table', cmd: 'highlight', args: { sel: ante.hits.map(id => `row:${id}`), tone: 'accent' } }] },
        { label: 'Confidence = {=supAB} / {=supA} = {=conf|2}', math: 'ratio', code: 'ratio',
          vars: { supAB: both.abs, supA: ante.abs, conf } },
      ],
    };
  }

  function frequentItemsets({ transactions, minsup }) {
    const items = sortSet([...new Set(transactions.flatMap(t => t.items))], ORDER);
    const supportMap = {};
    const frequent = [];
    for (const s of powerset(items)) {
      const abs = support({ transactions, itemset: s }).abs;
      supportMap[key(s, ORDER)] = abs;
      if (abs >= minsup) frequent.push({ itemset: s, abs });
    }
    return { supportMap, frequent, count: frequent.length };
  }

  // Quiz: confidence on a fresh small database
  function confidenceQ({ rng, difficulty, fns }) {
    const pool = ['bread', 'butter', 'cheese', 'eggs', 'milk', 'yogurt'];
    for (;;) {
      const n = difficulty === 1 ? 5 : 7;
      const transactions = Array.from({ length: n }, (_, i) => ({
        id: i + 1, items: sortSet(rng.sample(pool, rng.int(2, 4)), pool),
      }));
      const [a, b] = rng.sample(pool, 2);
      const r = fns.confidence({ transactions, A: [a], B: [b] });
      const supB = fns.support({ transactions, itemset: [b] }).abs;
      if (r.supA < 2 || r.supAB < 1 || r.supAB === r.supA || supB === 0) continue; // avoid trivial or undefined cases
      if (r.supA === n || supB === r.supA) continue;                                  // a misconception would equal the answer
      return {
        vars: { transactions, A: [a], B: [b], supAB: r.supAB, supA: r.supA, conf: r.conf,
                wrongDivN: r.supAB / n, wrongReversed: r.supAB / supB },
        misconceptions: [
          { var: 'wrongDivN', feedback: 'You divided by the number of transactions. Confidence divides by **Sup(A)**, the baskets that contain the antecedent.' },
          { var: 'wrongReversed', feedback: 'That is conf(B → A). Direction matters: divide by the support of the **antecedent**.' },
        ],
      };
    }
  }

  return { fns: { support, confidence, frequentItemsets }, generators: { confidenceQ } };
}
```

```js
    const applied = rate * actualBase;
```

## 7. Pedagogy rules

### 7.0 Guided learning: the loop every idea goes through

The site turns your files into a guided course. The **Path** tab lists each Intuition scene, then the Math sections whose skills that scene introduced, then the Application case, then a mastery check, with a "Continue" button that always points at the next unfinished step. Write the module so that following the Path, and nothing else, teaches the topic. Each idea goes through this loop:

| Step | What the learner does | Where it lives |
|---|---|---|
| 1. Goal | sees why this matters, as a concrete question | scene `goal`, manifest `objectives` |
| 2. Meet the terms | learns each new word at the moment the picture shows it | beat `define` (§7.1a) |
| 3. Predict | commits to an answer before the reveal | `predict` gate |
| 4. Do | changes the picture until something happens | `when` / `event` gates |
| 5. Watch it worked | sees every number of the lecture's example built step by step | StepPlayer walks (§7.5) |
| 6. Try it alone | solves the same kind of problem with fresh numbers, hints on request | `practice` gate |
| 7. Explain it | says why it works in their own words, then compares | `reflect` gate |
| 8. Formalize | reads the derivation next to the code or journal, steps through it | Math section |
| 9. Your turn | practices again with new numbers | section `tryIt` |
| 10. Apply | makes decisions in a realistic case | Application |
| 11. Master | mixed, spaced practice until every skill is solid | Quiz |

The Path is derived from your content, so scene order and section `skills` matter: a section is placed after the first scene by which all its skills have been introduced. Give every scene the `skills` it teaches.

### 7.1 Intuition (the 3Blue1Brown feel)
- **Open with a question or puzzle** (`goal`), not a definition. Concrete before abstract: show the lecture's own data first, then vary it.
- **One idea per beat**, ≤ 60 words. Narration explains the *idea*, never the UI ("drag the slider" is fine; "this widget displays…" is not).
- **Math grows out of the picture.** Put a `Formula` on stage and reveal it with `step` as the visual explains each part; highlight a term (`term:<anchor>`) at the moment the corresponding thing happens.
- **Count along, never skip to the end:** every lecture number is solved on stage, step by step (§7.5).
- **Predict before reveal:** at least one `predict` gate per scene. At least half of the scenes need an interactive gate (`when` or `event`) where the learner *does* something (drag, reorder, tune a parameter).
- **Continuity:** same widgets across beats; animate by changing state. Colors carry meaning consistently (`good` kept/frequent, `bad` pruned/wrong, `accent` current focus).
- **Surface insights and traps:** each module should have 1–3 "aha" scenes built on a surprising fact from the data (the FIM deck has *the milk trap*: conf = 1 but lift = 1).
- **Practice and reflect inside the story:** after a computation has been shown once, a `practice` gate makes the learner do it alone (≥ 3 per module, one per major skill); a `reflect` gate asks why it works (≥ 2 per module, §5.7).
- End every scene with a one-sentence `takeaway`. The takeaway card also lists the terms the scene introduced, automatically.
- **Size:** 6–10 scenes, 4–10 beats each; every skill appears in at least one scene. Order scenes to follow the lecture.

### 7.1a Terms and definitions are taught in Intuition

The glossary is not a list to memorize up front. Every term is **introduced inside a scene, at the beat where the picture first shows it**, and that is where the learner meets its definition.

- **Every glossary term is `define`d in exactly one beat** across the module (validated under guide 2). Put it on the beat whose narration first uses the term, typically in **bold** or as `[[term-id]]`, and whose stage shows the thing it names: define *Work in Process* while the job's costs are sitting in the WIP T-account, not in a list at the start.
- **The narration names the term** (lint). The definition card under it gives the glossary `short` definition, aka names and formula, so the narration doesn't need to repeat the definition word for word. It should say what the term *does* in this picture.
- **One to three terms per beat.** If a beat would introduce more, the scene is moving too fast: split the beat.
- **Define before use.** A term used in an earlier scene, section, prompt or explanation than the beat that defines it is a defect. Reorder, or define it earlier.
- **Afterwards, link it:** later narration, section summaries, quiz prompts and explanations write `[[term-id]]` (or `[[term-id|text]]`), so a learner who forgot can hover for the definition.
- **Look-alike terms get a contrast beat:** overapplied vs underapplied, product vs period cost, support vs confidence. Introduce the second term in a beat that sets it against the first, ideally with a `predict` gate that makes the learner choose between them.
- The site uses the defining scene as the term's lesson link in the glossary and in auto-generated glossary questions ("Show me in the lesson"), unless the term sets its own `lessonRef`.

### 7.1b Predictions must be real predictions

A predict gate only teaches if the learner commits *before* they can see the answer. Learner reviews found most "predict"
gates in early modules could be answered by reading the stage, so these rules are checked by a careful reviewer:

- **Nothing on stage gives the answer away while the gate is open.** A beat's `show` and `set` take effect *when the beat
  opens*, together with its gate. So the widget that prints the result (a Readout, a worksheet row, a Formula's last step,
  a coloured lattice, a finished walk, a T-account balance, a tone such as `tone: bad`) must stay hidden, unfilled or one
  step short on the gated beat, and appear on the **next** beat. Use `hidden: true` + `show` on the following beat, a
  worksheet `upTo` that stops before the asked row, `showBalance: false` until after the gate, or ask *before* the
  player runs ("Before playing: …"). The narration of the gated beat must not state the number either. Watch row
  *labels* too: a worksheet fn that blanks unreached amounts must also swap a label that carries arithmetic
  ("320 × 12.7133") for a plain one ("To finish beginning WIP") until that row is reached.
- **Ask for something new.** Don't ask the learner to add up addends the narration just listed, re-ask a fact answered
  two scenes earlier, or count dozens of items by eye (busywork). A `when` gate must not be satisfied on arrival: start
  the slider away from the target.
- **Options are shuffled for you.** Predict options and Application `mcq` decisions are shown in a fixed shuffled order
  (keyed by module, scene and beat), so write them in any order and never rely on position. Set `shuffle: false` only when
  the order carries meaning (ascending ranges, "less / same / more"). Make the wrong options plausible and the same
  length and tone as the right one: an option that alone is nuanced, cites a number, or echoes the question's wording is
  a giveaway. Options must not contain amounts that are already on stage.
- **Percent answers.** A numeric predict that asks "in %" or "as a percent" stores the answer in percent units and sets
  `percent: true` (`answer: { value: 98.59, tol: 0.01, percent: true }`), so `98.59`, `98.59%` and `0.9859` are all
  accepted. Quiz `numeric` and hand-calc answers take the same `percent: true` flag. In a gate a typed `%` is always
  understood (`18.7%` matches 0.187 or 18.7). Pick **one** convention per module (percent
  units in predicts and quiz prompts that say "%"; decimals when the prompt says "as a decimal") and say it in the prompt.
- **Tolerance matches the precision you ask for.** If the narration says "about ₱15.10", the tolerance must accept
  `15.10 × quantity`; otherwise state the decimals ("to 4 decimal places"). A tolerance must reject the misconception the
  scene warns about (F1 = 0.5714 with tol 0.005, not 0.01, because the plain average is 0.58).
- **Errata come after the gate.** Show an errata `Callout` on the beat after the learner answers the computation it
  corrects, prefixed "If you're reading the slide: …", never before or during the first computation.
- **No slide numbers in learner text.** "Slide 13", "Example 10", "Session 5" mean nothing to a self-learner and drift
  out of date. Keep slide references in `source` fields, SOURCE_NOTES and `examples`; in narration, prompts, hints and
  glossary entries refer to the lesson ("the Cavite example", "the job-order module").
- **Predict attempts count toward mastery**, so a give-away gate inflates a learner's mastery as well as wasting the beat.
- **Controls leak answers too.** A visible bound Choice or Slider lets the learner produce the answer before predicting
  (click "radius" and read the new accuracy). Keep such controls hidden until the gate's beat is over, then `show` them
  for a `when` gate. A Readout can't hide one item, so put answer-bearing items in their own hidden Readout. Bind
  answer-bearing props (`showRowMeans`, `showGain`, `showCosine`, `showBalance`) to a state key you flip after the gate.
- **Walks that end on the answer.** If a walk's last step prints the asked result (an average row, a final share), give
  the walk fn a stop-early parameter. On the next beat `hide` the player and `set` the progress key: an active patch
  overrides a beat's `set`. When beats and a walk both advance one worksheet, use two state keys and reveal up to the
  larger, so the beats never `set` a key the player patches.
- **Look backwards from every gate.** An earlier scene's examples, sort chips, closing line or reflect model must not
  state a later gate's answer. Re-read the lead-in to every gate after moving or merging scenes. After a `when` gate on
  a slider, `set` the exact state the next narration assumes (learners overshoot).

### 7.2 Math & Code / Math & Journal
- One section per formula or algorithm in the source, in lecture order. Derivations proceed in small steps: definition, then symbolic form, then live numbers.
- **Anchor every term that matters** in both panes (≥ 2 anchors per non-trivial section).
- **Step through the workbench on the lecture's data:** code line by line and iteration by iteration; a journal amount by amount, in the order an accountant works it (§7.5).
- Give the live example the lecture's numbers, and list the matching `examples`.
- Pitfalls come from real mistakes (they should mirror your quiz misconceptions). An exam tip is one practical sentence.
- Add sections that go beyond the slides only when they're genuinely useful (for example, regularization in ALS), and mark them `beyondSlides: true`.
- **End every section with `tryIt`:** 1–3 quiz templates on that section's skill, ideally one computation and one workbench template (`code-fill`, or `journal-entry` / `schedule-fill`).

**Journal workbench (accounting) rules**
- **Account titles exactly as the lecture prints them**, everywhere (journal, quiz `accounts`, glossary): "Work in Process" and "Work-in-Process Inventory" are different strings to the grader. Record the lecture's chart of accounts in SOURCE_NOTES.
- **Entries the way the lecture writes them:** debits first, credits indented below, one entry per event, a short memo (the lecture's explanation line). Split compound entries only if the lecture does. Keep entries ≤ 8 lines.
- **The derivation computes, the journal records.** A typical section's journal pane is a schedule that computes the amounts (cost sheet, rate computation, variance table) followed by the entries that record them, with the same anchors on both.
- **Normal balances and signs:** amounts are positive; the side carries the meaning. Say the normal balance in the glossary for accounts the lecture emphasizes.
- **Statements and schedules** (contribution-margin income statement, cost of goods manufactured, production report, budgets) are `schedule` blocks: labels indented as printed, `style: subtotal` / `total` for the rules, `format` for units, percents and per-unit amounts, `columns` for Total / Per unit / % or Dept A / Dept B.
- **T-accounts** show the flow of costs. Build them with a worksheet fn and a walk fn (§7.5) so postings appear one entry at a time.

### 7.3 Application
- Keep one coherent story from start to finish, and connect it to prior modules when relevant (`connections`).
- Include ≥ 3 `decision` cells where the learner must *interpret* results (which rule to act on, which recommender to trust, why a metric misleads).
- **Make the learner do the work.** Cell widgets are always visible, so a cell must not show the number its decision asks for (no Step 5 schedule next to "what is ending WIP worth?"), and its prompt must not state the answer ("the methods differ by ₱125, what does that mean?"). Give the inputs, ask for the result, and write `mcq` options computed from real mistakes (leaving out beginning cost, the wrong divisor…). At least one decision should require a computation the lesson taught.
- Numbers in different cells must tell one consistent story: if two cases look alike but are treated differently (prorated vs closed), say what differs.
- **Every cell is visible at once,** and so is the case story. Neither may state what a later decision asks. Mark an
  answer-bearing widget `hidden: true`: it then appears only after that cell's decision is answered. Don't derive a
  cell's asked figure from state another cell toggles (pin it, or give the inputs). For "which and by how much"
  decisions, give every option the same shape (who, amount), each distractor a computed mistake. Use `optionFeedback`
  to explain the specific error behind each wrong option.
- Always include `atScale`, `tradeoffs` and `explainBack`.

### 7.4 Quiz bank quotas (minimum per module)
- **≥ 25 templates**, **≥ 2 per skill**.
- ≥ 8 generator-driven `numeric` or `hand-calc` · ≥ 2 `hand-calc` that mirror the lecture's worked procedure step by step · ≥ 6 conceptual `mcq`/`multi` · ≥ 4 workbench templates (`code-fill` for code; `journal-entry` + `schedule-fill` for journal, at least one of each when the lecture has both entries and statements) · ≥ 2 `order` · ≥ 2 `match`.
- `hints` on at least half the templates, including every numeric, hand-calc, journal-entry and schedule-fill template.
- Every numeric template has **≥ 2 misconceptions**. MCQ distractors should be *plausible wrong answers* (ideally computed from misconceptions), never joke options.
- Difficulty spread is roughly 40% level 1, 40% level 2, 20% level 3.

### 7.5 Count along and solve along
A learner should be able to reproduce **every** number in the lecture with pencil and paper by following the lesson. Showing a finished table, similarity matrix, FP-tree or lattice and then explaining it is a defect: build it in front of them, one number at a time.

**Intuition scenes**
- **Solve every number, not a sample.** Each similarity pair, each candidate's support, each rule's confidence and lift, each cell of an update gets its own step with the arithmetic written out, e.g. `$\frac{4\cdot3 + 2\cdot5}{\sqrt{20}\,\sqrt{34}} = 0.84$`. Work the first case slowly across beats (with a `predict` gate before the result), then let a walk player do the rest at the same level of detail.
- **Count visibly.** For support, tick every basket that holds the itemset (a basket × candidate `Matrix` of `\checkmark` / `\cdot` cells, or `annotate` on table rows) and show the tally as a sum: `$1+0+1+1+0 = 3$`. For FP-growth, show the item counts, the reordered and filtered baskets, the tree growing one insert at a time, then each conditional pattern base and its counts. Nothing appears already finished.
- **Worksheet fn + walk fn + `patch`.** Write a derived fn that renders a partly filled worksheet from a progress param (`supportGrid({…, upTo})` returns Matrix `values` with TeX cells for solved entries and `''` for unreached ones). Write a trace fn (a "walk") whose steps advance that param with `patch: { gridUpTo: 7 }`. Declare the key in the scene `state`, feed it to the derived fn in `derive` (`upTo: '@gridUpTo'`), and bind the widget to the result (`values: '@g.values'`). The Matrix, Tree or ItemsetLattice then fills in as the player steps, and seeking back rewinds it. See `fim` scene `lecture-support-table`.
- **Patch pitfalls.** A patch applies only while its player is on stage (hiding the player drops the patch and any `fill`ed cells, so keep it visible to the end of the scene or `set` the final values in the next beat). A player's `in` must not read a key it patches. Patch only keys the beats don't `set`, because an active patch overrides beat state.
- **Posting a ledger entry by entry with gates in between:** bind the Journal's `posted` and the TAccounts'
  `showBalance` to scene state and advance them with beat `set` instead of a StepPlayer, whose patch fights beat state
  and whose full replay shows the balances being asked. In an Application cell, `posted: [ids]` shows a journal minus
  the entry the decision asks the learner to record.
- **Labels carry the arithmetic.** Put the numbers in `$…$` (each math run counts as one word toward the 20-word label limit) and the *why* in words: "T3 holds bread and milk → tick. $1+0+1 = 2$ so far."

**Math & Code sections**
- **Write loops, not one-liners.** The code the learner steps through is plain Python that does one visible thing per line on the lecture's data. The idiomatic numpy/pandas version can go in `extraCode`. Keep each block ≤ 30 lines.
- **Anchor every line that changes data,** and give each code anchor a TeX partner and a `links` entry. A derivation step such as "the loop in math" (`\anchor{acc}{s \mathrel{+}= r_{ui}\,r_{vi}}`) usually provides the partners.
- **One trace step per executed line, per iteration.** The trace follows the loop exactly as Python would run it (`for` → `if` test → accumulate, for every iteration), with `vars` holding the current loop variables and the running value (`i: 'bread'`, `acc: 7`). Math & Code uses `label`, `code`, `math` and `vars`, and applies `ops` to the live-example widgets (§5.8); it ignores `patch`. **Give every step ops** that show its line on the data: highlight the row, cell or chips the line reads, and annotate or fill what it writes. Stay ≤ 400 steps: on large inputs, trace one full outer iteration line by line and give each remaining iteration a single summary step.

**Math & Journal sections**
- **One trace step per amount, in the order an accountant works it:** each schedule row as it is computed (with the arithmetic in the label: "Overhead applied $= 1{,}200 \times 15 = 18{,}000$"), then each entry as it is recorded. `code` names the journal anchor to light, `math` the derivation anchor, and `ops` with `role: journal` highlight or annotate rows (`row:<id>`), entries (`entry:<id>`), lines (`line:<entryId>:<n>`) or accounts (`account:<name>`) in the pane.
- **Every entry the lecture shows** appears in some section's journal, and every statement the lecture builds is built row by row in a scene (Schedule widget + worksheet fn + walk fn) before it appears finished in a section.

**Tests.** Add an `examples` entry for every walk fn (how many cases it visits and its final result), so a later edit can't quietly shorten the count-along.

### 7.6 Plain language: the learner starts from zero

Assume the learner knows **nothing** about the subject: not the course's earlier sessions, not its jargon, not the
libraries. They can read, do school arithmetic and follow a picture. Every module stands on its own, even when other
modules in the same course define the same words. Learners report modules as "hard to understand" far more often because
of unexplained words than because of hard ideas.

- **Basics are terms too.** The words an expert stops noticing are the ones that lose a beginner: *model / classifier,
  feature, training set, test set, prediction, probability, correlation, p-value, decision tree, regression, residual,
  threshold*. If the lecture leans on one, give it a glossary entry and `define` it in an early beat, before the topic's
  own terms build on it.
- **Explain every symbol the first time it appears,** in words, in the same beat: "$y_t$ ('y at time t') is the value
  now", "λ ('lambda') is a random number between 0 and 1", "Δ means 'change'". Name Greek letters when you introduce them.
- **One symbol, one meaning, one index order.** Don't let `v₁₂` mean "item 1, factor 2" in one scene and "factor 1,
  item 2" in the next, or let `σ`, `K`, `I` or `Sup` change meaning between sections. Pick one convention, use it in
  every file, and if the lecture writes it differently say so once ("the lecture writes v_js; we write v_sj").
- **Short sentences, everyday words.** Aim for 8–15 words per sentence and one idea per sentence. Prefer *use* to
  *utilize*, *about* to *approximately*, *mixed* to *heterogeneous*, *copy* to *duplicate*, *make* to *synthesize*.
  Keep the technical word when it is the term being taught; replace it everywhere else.
- **Say what a term does before what it is called.** "Copy random minority rows until the groups are equal. This is
  **random oversampling**." The name is a label for an idea the learner already has.
- **No unexplained acronyms or names.** Spell out an acronym once (ROC-AUC, SAGIP, ADF) and say in a few words what it is
  for. Library and function names (`rolling(3)`, `TreeExplainer`) need a plain-language gloss the first time.
- **Goals and quiz prompts are learner-facing too.** A scene `goal` asks its question in everyday words and does not use
  the terms the scene is about to teach. Prompts, options, hints and explanations use only terms already defined on the
  Path (or link them with `[[term-id]]`).
- **Glossary `short`s are for beginners.** One plain sentence a newcomer could repeat to a friend. Put the formula in
  `formula` and the nuance in `long`, not in `short`.
- **Check the order on the Path, not just in the file.** A Math section appears right after the first scene that covers
  all its skills (§7.0). Its summary must not link a term that a later scene defines; if it would, move the definition
  earlier or adjust the scene's `skills`.

## 8. Correctness rules (what the validator and a careful reviewer check)

1. Every lecture number you cite reproduces from `logic.js` (examples pass).
2. The conventions in `SOURCE_NOTES.md` explain *why* those numbers come out that way.
3. Errata are logged, not silently "fixed". Lessons show the correct value plus a `Callout` of kind `errata`.
4. Python in `math-code` computes the same thing as the JS fn it sits next to.
5. Quiz answers come from `fns` (no hand-typed answers for generated questions).
6. Every reference resolves: widgets, fns, generators, datasets, `@refs`, `{=paths}`, anchors, `lessonRef`s, skill IDs, glossary `related`.
7. IDs are unique and kebab-case; `requires.widgets` lists exactly the widgets used.
8. Every journal entry balances (static entries at import; '@ref' amounts with the initial inputs), every journal amount resolves to a number, and every journal-entry quiz answer balances and uses only accounts from its `accounts` list.
9. Every glossary term is `define`d in some beat, and every `[[term]]`, `define`, `practice` template and `tryIt` id exists.
10. Lints (warnings) also flag: a numeric predict whose beat narration states the result ("= 75"); a generator misconception that lands within tolerance of the answer in more than 10% of seeds.

## 9a. Animations (HyperFrames renders)

Some parts of a lesson are **stale**: a definition, a cause and its effect, a process, a framework, something that
changes over time. The catalog widgets can only show these as text or a still picture. For those moments a module can
ship a short **animation**: a 3–8 second, silent, looping clip in a flat motion-graphics style (think Kurzgesagt),
composed in [HyperFrames](https://github.com/heygen-com/hyperframes) (HTML + GSAP, with Three.js for 3D), rendered to a
video file, and played on stage by the `Animation` widget.

### 9a.1 When to animate, and when not to

- **Animate what moves or changes:** costs flowing from Raw Materials to Work in Process, a tariff pushing prices up
  the supply chain, baskets being scanned for an itemset, two vectors turning until they line up, a surface in 3D.
- **Don't animate the work the learner should do.** Count-along (§7.5) stays in the interactive widgets. A clip can
  pose the scene's question or show what a result *means*; it never produces the number a gate asks for.
- **Never give a gate away (§7.1b).** A clip on stage while a predict gate is open must not show the answer: put it
  on the beat after the gate (`hidden: true`, then `show`), or end the clip before the reveal.
- **One idea per clip, at most one clip per scene,** usually 3–8 per module. Each clip sits next to a beat whose
  narration explains it. Clips are silent and nearly wordless (≤ 6 words on screen, large): the narration carries the
  words, because text burned into video can't be searched, translated or read by a screen reader.
- **Terms are still taught in beats.** A clip can show what a term means, but the beat still `define`s it (§7.1a), and
  on-screen words use the glossary's spelling.
- **Numbers on screen come from the module.** If a clip shows ₱600,000 or 0.67, that value must be what `logic.js`
  and the datasets give, so the clip and the lesson never disagree.

### 9a.2 The workflow

| Step | Where | Result |
|---|---|---|
| 1. Plan | chat or repo | one brief per clip in `ANIMATIONS.md` (§9a.3) |
| 2. Compose | repo, with the HyperFrames skills (`npx skills add heygen-com/hyperframes`) | one HTML composition per clip in the repo's HyperFrames project, `animations/clips/<module-id>/<clip-id>.html`, built on the shared motion kit in `animations/kit/` (§9a.7). The project lives **outside** `modules/`, so it never ships in a module or the Docker image |
| 3. Check | `pnpm anim:lint`, `pnpm anim:preview` (Studio), or `pnpm anim:render --draft <clip-id>` | a clip that follows §9a.4 |
| 4. Render | `pnpm anim:render <clip-id>` runs `npx hyperframes render animations -c clips/<module-id>/<clip-id>.html --format webm --fps 30 --quality high` … | any HyperFrames output (§9a.5) |
| 5. Convert | … then `pnpm kodigo animation animations/renders/<clip-id>.webm modules/<module-id>/assets/anim/<clip-id> --flatten --bg '#0B1D3A'` (the same command step 4 runs; use it alone for renders made elsewhere) | `<clip-id>.webm`, `<clip-id>.mp4`, `<clip-id>.poster.jpg` and the YAML to paste |
| 6. Place | the module's YAML | an `Animation` widget on a stage, shown on its beat (§9a.6) |
| 7. Validate | `pnpm kodigo validate modules/<module-id>` | clean |

**Chat mode does step 1 only.** It writes `ANIMATIONS.md` and places **no** Animation widgets: a pasted text bundle
can't carry video files, and an Animation whose file is missing fails validation. A repo session later renders the
briefs and adds the widgets. Once a module's clips are installed, re-importing it from a pasted bundle (a fix request,
a text revision) keeps them: the server keeps the installed version's `assets/` and `sources/` files the paste doesn't
include. To add or replace a clip, import a **zip or folder**, or work in the repo.

### 9a.3 `ANIMATIONS.md` (optional; the brief for each clip)

Not shown to learners. It's the storyboard a HyperFrames session works from, and the record of what each clip must and
must not show. One `##` section per clip, keyed by the clip id (kebab-case; it becomes the file name and the widget id):

```markdown
# Animations: <module title>

## overhead-spreads
- Where: intuition › why-a-rate › after the predict gate (stage widget `overhead-spreads`, region main)
- Idea: a fixed pile of overhead is shared by every labor-hour, so fewer hours make each hour dearer.
- Length: 6 s, loops · Shape: 16:9 · Background: opaque, the module colour #b45309 on cream
- Storyboard:
  - 0.0–1.5 s: a pile of peso coins labelled "Overhead" drops onto a factory floor.
  - 1.5–4.0 s: the coins split evenly onto 8 clocks (labor-hours); each clock gets a small stack.
  - 4.0–6.0 s: 4 clocks fade out; their coins slide onto the remaining 4, whose stacks double.
- On-screen words: "Overhead", "per hour"
- Numbers: none (the beat computes ₱15 per hour)
- Must not show: a rate in pesos (the practice gate on the next beat asks for one)
- 3D: no
```

### 9a.4 Composing for Qdigo (house rules)

- **Size and timing:** `data-width="1280" data-height="720"` (16:9; use 1080 × 1080 for a square clip in a side
  region), 30 fps, `data-duration` 3–8 s. Hold the final state for about half a second, or make the last frame match
  the first so the loop is seamless.
- **Paint the background.** Clips are opaque by default: give the root a background colour that works on both themes,
  or render a second version for dark mode (`srcDark`). Transparency (unpainted background, rendered to `.webm` or
  `.mov`) works in Chrome, Edge and Firefox but not reliably in Safari, so use it only for clips that still read on a
  solid fill.
- **Style:** flat vector shapes, a small palette (3–4 colours plus the module's `color`), thick outlines, soft
  shadows, simple characters and icons that stay the same across a module's clips. Large type when there is any.
- **Silent:** the site always plays clips muted. Leave out audio tracks.
- **Deterministic:** HyperFrames renders by seeking, so every frame must be a pure function of time. One paused GSAP
  timeline registered on `window.__timelines['<composition-id>']`; no `Math.random()` without a fixed seed, no clocks
  (`Date`, `performance.now`, `requestAnimationFrame` loops), no network requests, and finite repeats (never
  `repeat: -1`; the site loops the clip). Keep fonts and images inside the project.
- **Three.js:** drive the scene from the timeline (tween plain objects with GSAP and render the scene from the
  timeline's time, or use the HyperFrames Three.js frame adapter as its docs describe); never animate on Three's own
  clock. Keep scenes light (a few hundred objects): it's an illustration, not a game.
- **Accessible motion:** no flashing (more than 3 flashes a second), no full-screen strobing, gentle camera moves.
  Learners who ask for reduced motion see the poster (for a segment: its last frame), so the **poster frame** (by
  default the last frame) should show the idea on its own. Their Play button shows the clip as 3–4 still frames that
  crossfade: list those times in `stills`.

### 9a.5 Formats: what the site plays

`pnpm kodigo animation` converts any of these into a VP9 `.webm` (keeps transparency), an H.264 `.mp4` (plays
everywhere; transparency flattened onto `--bg`) and a poster still. Convert even when the render already plays: the
converter also scales to ≤ 1280 px, strips audio, adds the fast-start flag and writes the poster.

| HyperFrames `--format` | Plays as is? | Notes |
|---|---|---|
| `mp4` (default) | yes | opaque only |
| `webm` | yes | keeps transparency |
| `mov` (ProRes 4444) | **no**, Safari only | convert |
| `gif` | yes, as an animated image | can't seek or report `ended`, and is large: convert |
| `png-sequence` | yes, as a frame folder (`src: assets/anim/<clip-id>/`, `fps`) | ~20× larger than video: convert |
| `hls` | **no** | convert the folder |
| the composition `index.html` | **no** (needs the HyperFrames runtime) | render it first |

Converter options: `--width <px>` (default 1280), `--fps <n>` (frame folders; default 30), `--poster end|start|<seconds>`
(default `end`), `--flatten` (drop transparency), `--bg '#hex'` (the colour transparency is flattened onto, default
white), `--crf-webm <n>` / `--crf-mp4 <n>` (higher = smaller), `--no-mp4`, `--no-webm`. It needs `ffmpeg` and `ffprobe`
on the PATH, which HyperFrames needs too.

**The validator checks** that every `src`, `srcDark`, `poster` and `posterDark` file is in `assets/`, that its format
plays (a `.mov`, `.m3u8`, `.html` or unknown file is an error that names the converter command), that a `src` list
doesn't mix videos with images, that a frame folder has at least 2 frames, that `end` comes after `start`, and warns
about any file over 8 MB. Aim for 0.3–3 MB per clip: a module import is one upload, capped by the server's `MAX_UPLOAD_MB` (30 MB by default, which leaves room for about 20 MB of assets once the admin page encodes them).

### 9a.6 Placing a clip

```yaml
stage:
  - id: overhead-spreads
    widget: Animation
    hidden: true                       # appears on the beat after the predict gate
    props:
      src: [assets/anim/overhead-spreads.webm, assets/anim/overhead-spreads.mp4]
      poster: assets/anim/overhead-spreads.poster.jpg
      alt: A pile of overhead coins is shared by fewer and fewer labor-hours, so each hour carries more.
beats:
  # … the predict gate on the rate comes first …
  - say: |
      Watch what happens to each hour's share when the factory works **fewer** hours.
    show: [overhead-spreads]
    do: [{ target: overhead-spreads, cmd: restart }]
    gate: { type: event, prompt: Watch it once., target: overhead-spreads, event: ended }
```

- **`src`** lists the same clip in several formats, best first; the browser plays the first it can. Keep `.webm`
  first and `.mp4` second.
- **`alt`** (required) says in one sentence what the clip shows. Screen readers read it, and the stage shows it if the
  file is missing.
- **Behaviour:** muted, loops (`loop: false` to stop at the end), plays while at least a third of it is on screen and
  pauses when scrolled away (`autoplay: false` to wait for the learner), with play/pause and restart buttons and a thin
  progress bar (`controls: false` for a purely decorative loop). `rate`, `start`/`end` (a segment, in seconds),
  `width`, `aspect` (reserve the clip's shape before it loads; default `'16:9'`), `caption` and `bare` (no card
  frame) are in §9 and `WIDGETS.md`.
- **Reduced motion:** clips never start by themselves. The learner sees the poster (for a segment, the segment's last
  frame) and a play button that shows the `stills` (3–4 key-frame times; default four evenly spaced frames) as
  crossfading still frames. A beat's `play` or `restart` command only rewinds the clip.
- **One clip across several beats:** to step through a clip in time with the narration, put one widget on stage with
  `start: '@animFrom'` and `end: '@animTo'`, declare both keys in the scene `state`, and `set` them on the beats that
  move on (`set: { animFrom: 2.6, animTo: 5 }`). The clip stays on stage and plays the new segment in place; going back
  a beat plays that beat's segment again. Use `loop: false` so each segment holds its last frame, and make sure no
  segment shows a number a gate asks for while that gate is open.
- **Commands:** `play`, `pause`, `restart`, `seek {t}`, plus `highlight`/`pulse`/`annotate` on the selector `frame`.
  A StepPlayer trace can address a clip by role like any widget.
- **Event:** `ended` fires each time a video or frame-folder clip reaches its end (on every pass when looping), so an
  `event` gate can wait for one full viewing. Event gates are skippable by default; keep them so for clips. Animated
  images (`.gif`/`.webp`) never emit `ended`.
- **Dark theme:** `srcDark` and `posterDark` switch with the site's theme.
- **Anywhere a stage exists:** Intuition scenes, a Math section's `live` widgets, an Application cell's `stage`, a
  quiz template's `show`. List `Animation` in `manifest.requires.widgets`.

### 9a.7 The repo's motion kit (`animations/`)

`animations/` is one HyperFrames project. `index.html` is a short style card; each clip is
`clips/<module-id>/<clip-id>.html`, a full page whose scene script is inline (the HyperFrames linter reads inline
scripts) and which loads the shared kit:

```html
<link rel="stylesheet" href="../../kit/kit.css">
<script src="../../kit/vendor/gsap.min.js"></script>
<script src="../../kit/kit.js"></script>
…
<div id="stage" data-composition-id="<clip-id>" data-start="0" data-width="1280" data-height="720" data-duration="5"></div>
<script> /* the scene: HF.timeline(5), window.__timelines['<clip-id>'] = tl, shapes, choreography */ </script>
<script type="module" src="../../kit/kit-three.js"></script>
```

The kit draws the house look (navy → indigo sky with drifting specks in Three.js, Nunito labels) and gives each scene
helpers that enforce the motion rules: `HF.timeline(seconds)`, layers and a heads-up layer the camera doesn't move,
flat shapes with one highlight and one shade (`HF.box`, `HF.disc`, `HF.coin`, `HF.coinStack`, `HF.character`,
`HF.cap`, `HF.wave`…), labels (`HF.label` + `HF.say`), pop-ins with a 110% overshoot (`HF.pop`), moves that settle with
a wobble (`HF.move`, `HF.wobble`, `HF.land`), arcs for coins (`HF.arc`), numbers that count up (`HF.count`), slow camera
pushes (`HF.camera`), bounded loops (`HF.loop`, `HF.bob`) and seeded randomness (`HF.rng`). Every frame is a pure
function of the timeline's time, so HyperFrames can seek it. Copy an existing clip as a starting point.

## 10. When the catalog isn't enough

Don't invent widgets, props or commands. Instead:
1. Build the best approximation from catalog widgets. Most things can be done with `Matrix`, `Chart`, `Tree`, `DropBins`, `Formula` and `Callout`.
2. Add `WIDGET_REQUESTS.md` describing the widget you wish existed: name, purpose, props, selectors, commands, events, the scene that needs it, and your fallback. The site owner can add it to the catalog, and a later module version can use it.
3. If what you need is motion the widgets can't express, plan an animation instead (§9a).

## 12. Self-check before you output

- [ ] `SOURCE_NOTES.md` lists every concept, formula and worked example, with slide refs; conventions have evidence; errata have reasons.
- [ ] Every worked numeric result from the lecture is in `examples.yaml`, and I verified each one against `logic.js`.
- [ ] `logic.js` has no imports, `Math.random`, `Date` or DOM; every fn returns a plain object; every trace role is documented.
- [ ] Every generator redraws on ambiguous or degenerate cases and computes answers through `fns`.
- [ ] Every `@ref` and `{=path}` resolves in its scope; no scope-name collisions.
- [ ] Every TeX `\anchor{x}` has a code `@a x` in the same section and vice versa; every anchor appears in `links`.
- [ ] Only catalog widgets, props, commands and selectors are used, and `requires.widgets` matches exactly.
- [ ] Quotas are met: 6–10 scenes; a predict gate in every scene; interactive gates in ≥ 50% of scenes; ≥ 25 quiz templates; ≥ 2 per skill; type mix per §7.4; ≥ 2 misconceptions per numeric template.
- [ ] Every lecture number is solved step by step in some scene (no finished tables dropped on stage), and every math-code trace walks each loop iteration line by line (§7.5).
- [ ] No predict gate can be answered from the stage, a worksheet label or the narration when it opens; `when` gates are not satisfied on arrival; errata come after the gate; percent answers use `percent: true` (§7.1b).
- [ ] No slide, session or example numbers in learner-visible text; every claim ("this check catches X", "λ fixes Y") was tested in `logic.js`.
- [ ] Generator misconceptions are keyed with `for`, never land within tolerance of the answer, and prompts state the rounding they expect (§5.10).
- [ ] Application decisions make the learner compute or judge: the asked number is not on that cell's stage or in its prompt (§7.3).
- [ ] `manifest.course` is set to the course code the user gave (same spelling as that course's other modules), and `guide: 2` and `workbench` are set.
- [ ] 3–6 `objectives`, each a checkable "can do" sentence tied to skills; together they cover every skill.
- [ ] Every glossary term is `define`d in exactly one beat, at its first use, and that beat's narration names it; later mentions use `[[term-id]]` (§7.1a).
- [ ] A complete beginner could follow it (§7.6): basic words (model, feature, training/test set, probability, correlation…) are glossary terms defined early; every symbol and acronym is explained the first time; goals and prompts use only words already taught; sentences are short and plain.
- [ ] ≥ 3 `practice` gates and ≥ 2 `reflect` gates; every math section has `tryIt`; at least half the templates (and every numeric, hand-calc, journal-entry, schedule-fill) have `hints`.
- [ ] Animations (if any): each has a brief in `ANIMATIONS.md`, its files in `assets/anim/` (converted with `pnpm kodigo animation`), an `alt`, a poster, and no clip shows the answer of a gate that is open while it plays (§9a). Chat mode: briefs only, no Animation widgets.
- [ ] Journal workbench: every section has a `journal` pane; every lecture entry and statement appears; account titles match the lecture exactly; every entry balances; amounts are positive.
- [ ] Every skill appears in manifest, scenes, sections and quiz templates; every `lessonRef` points to an existing id.
- [ ] Every math-code function has a docstring, and every trace step carries `ops` that show its line on the live-example widgets.
- [ ] Word limits are respected; there are no placeholder texts, "TODO"s or "…" anywhere.
- [ ] YAML follows §4.8 (TeX in `|` blocks or single quotes, refs quoted).
- [ ] The output is one bundle in the §3.2 format, with every file complete.

## 13. Common mistakes to avoid

- Picking a formula variant from memory instead of the lecture's (e.g., Pearson over all items when the lecture uses co-rated items only). **The lecture's numbers decide the convention.**
- Forgetting a step the lecture leaves implicit (e.g., adding μᵤ back after a mean-centered prediction). Teach it explicitly and note it in SOURCE_NOTES.
- Generators that produce ugly decimals, ties at the k-th neighbor, or divisions by zero.
- Misconception values equal to the right answer for some seeds (redraw).
- Narration that restates the formula in words without the *why*.
- Skipping to the end: showing the final support table, similarity matrix or FP-tree without computing each entry in front of the learner, or a code trace that jumps over loop iterations.
- Computation embedded in YAML: all numbers come from `logic.js` or datasets.
- Renaming IDs when revising. Add new ones and retire old ones instead (removed IDs simply stop appearing).
- Double-quoted TeX in YAML (`"\frac"` breaks). Use `|` or single quotes.
- Writing for a classmate instead of a beginner: jargon from earlier sessions ("held-out", "metric", "node", "H₀") used as if known, Greek letters and subscripts never read aloud, scene goals that use the very terms the scene teaches (§7.6).
- Defining terms in a glossary-dump beat ("Here are the key terms: …") instead of at the moment the picture shows each one, or using a term in narration before the beat that defines it.
- A `practice` gate before the scene has shown the computation once (the learner has nothing to imitate), or a `reflect` prompt that just asks for a definition. A practice template that uses ideas taught *later* (beginning WIP before weighted-average) also fails: give the scene a simpler difficulty-1 variant.
- Starting a story and dropping it (June's numbers set up, then never used), or switching to a company the narration hasn't introduced. When a scene changes example, say why and give the new example's facts.
- Breaking the Path order. Math sections are placed in file order after the scene that introduces all their skills, and
  one early section holds back every later one, so keep section order aligned with scene order. Don't give a hook
  scene a skill whose section would then jump ahead of the scene that defines its terms; when you move a scene, retag
  the sections that depend on it.
- Quoting per-case numbers (one patient's SHAP bars, a slide's figures) that SOURCE_NOTES doesn't record. Teach the
  reading on a toy example, phrase quiz items as hypotheticals, and log the gap.
- TeX in Matrix `rows`/`cols` labels: labels render as plain text; only cell values are TeX.
- A review module that re-teaches other modules without saying so. State it in the summary and first beat, and bridge
  differing conventions (account titles, allocation basis, report formats) in glossary `long` fields rather than
  renaming accounts the journal grader matches.
- Teaching a check as catching errors it mathematically can't. Before you write "this test detects X", try X in `logic.js` and confirm the check fails.
- Animations that do the learner's work (the clip computes what the next gate asks), that carry the explanation in burned-in text instead of the narration, that show numbers `logic.js` doesn't produce, or that reference a `.mov`/`.gif`/frame folder straight from the render instead of the converted `.webm` + `.mp4`.
- Journal: an account title spelled differently in the quiz than in the lesson; a static entry whose sides should flip with the inputs (build it in logic.js); negative amounts instead of the opposite side; unquoted titles containing commas in YAML flow maps (`{ title: 'Job cost sheet, Job 101' }`).

## 14. Revising a module and answering fix requests

- **Fix request from the importer:** output **only the files listed**, each **complete**, in bundle format, with the same `id` and `version` unless told otherwise.
- **Content revision:** bump `version` (patch for fixes, minor for new scenes or templates), keep all existing IDs, and add a line to `authoring.notes`.
- **Adding animations to an existing module:** add the clips and widgets in the repo (or import a zip), give each clip a new widget id, and bump the minor version. A later text-only fix request keeps the installed clips.
- **Splitting a module:** the new module gets a new id; the old one keeps its ids for the content that stays.
- **Upgrading an edition-1 module to guide 2:** add `guide: 2` and `objectives`; add `define:` to the beat where each glossary term first appears (the validator lists the missing ones); add practice and reflect gates, `tryIt`, and `hints`; bump the minor version. Existing ids don't change, so progress carries over.
